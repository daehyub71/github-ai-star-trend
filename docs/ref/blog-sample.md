이름만 아는 가게 — 이름과 위치는 다른 정보

친구가 "오늘 저녁은 골목 끝 책방 카페에서 보자"고 메시지를 보냈습니다. 이름은 알지만 어디 있는지는 모릅니다. 지도 앱에 이름을 검색하면 지도가 실제 위치를 찾아 주고, 그제야 길을 따라가 가게 문을 열 수 있습니다. 이름과 위치는 서로 다른 정보입니다.

컴퓨터도 같습니다. 사람은 example.com처럼 외우기 쉬운 이름을 입력하지만, 네트워크에서 목적지를 찾아 데이터를 전달할 때는 IP 주소가 필요합니다. 이름을 주소로 바꿔 알려 주는 체계가 바로 DNS입니다.

다만 「이름 하나에 숫자 하나」는 간단한 첫 그림일 뿐이고, 큰 서비스는 주소를 여러 개 씁니다. 이 글에 나오는 IP 주소는 모두 문서에 예로 쓰라고 따로 떼어 둔 범위이거나 집 안에서 쓰는 사설 범위라서, 실제로 접속하는 곳이 아닙니다.

IP 주소는 주민등록번호일까

IP 주소를 컴퓨터의 주민등록번호라고 부르기도 하지만, 평생 하나로 고정된 번호는 아닙니다. 행사장에 들어갈 때마다 새로 받는 좌석 번호에 더 가깝습니다. 오늘 카페 와이파이에서 노트북이 받은 주소가 내일 집에서 받은 주소와 같을 이유는 없습니다. 와이파이와 유선을 함께 쓰는 컴퓨터는 주소를 여러 개 가질 수도 있습니다.

가장 많이 보는 형태는 IPv4입니다. 192.0.2.10처럼 점으로 구분한 네 개의 숫자이고, 각 숫자는 0부터 255 사이입니다. 이 방식으로 만들 수 있는 주소는 약 43억 개뿐이라 세상의 기기를 다 담기에 모자랍니다. 그래서 2001:db8::10처럼 훨씬 긴 IPv6도 함께 씁니다. IPv6는 콜론으로 칸을 나누고, 0이 이어지는 부분은 콜론 두 개로 줄여 씁니다. 그러니 IP 주소는 반드시 숫자 네 덩어리라고 외우지 마세요.

도메인은 인터넷의 간판 — 오른쪽으로 갈수록 큰 단위

도메인은 사람이 기억하기 좋게 붙인 이름, 말하자면 인터넷의 간판입니다. 읽을 때 알아 둘 것이 하나 있습니다. 오른쪽으로 갈수록 큰 단위입니다.

shop.example.com — 오른쪽 끝 com이 최상위 도메인, 그 왼쪽 example이 등록된 이름, 맨 왼쪽 shop이 하위 도메인

example.co.kr — 한국(kr), 그 안의 기업용 구역(co), 그 안의 example 순서로 읽는다

daehyub71.github.io — io가 최상위, github가 등록된 이름, daehyub71이 하위 도메인

마지막 줄은 오늘 예제 사이트의 이름입니다. github.io는 GitHub가 등록한 이름이고, GitHub가 계정마다 그 아래에 하위 도메인을 하나씩 만들어 줍니다.

간판은 들고 이사한다

가게가 이사를 갑니다. 옛 건물에는 간판 자국만 남았고, 주인은 간판을 그대로 들고 길을 건너 새 건물에 같은 간판을 겁니다.

여기서 간판은 도메인을, 건물 주소는 IP 주소를 빗댄 것입니다. 서비스를 다른 클라우드로 옮겨 IP 주소가 바뀌어도, 도메인 설정만 고치면 손님은 같은 이름으로 찾아옵니다. 이름과 주소를 따로 관리하는 까닭입니다.

실제 사이트 주소 읽기 — 서울 상권 인텔리전스

이번 장부터 새 예제입니다. 서울의 상권을 분석해 보여 주는 「서울 상권 인텔리전스」라는 공개 저장소입니다.

https://github.com/daehyub71/seoul-trade-insight

저장소 설명서인 README 맨 위에는 실제로 열리는 사이트 주소 한 줄과, GitHub Pages로 자동 배포한다는 말이 적혀 있습니다.

https://daehyub71.github.io/seoul-trade-insight/

https — 통신 방식 / 포트를 적지 않았으니 https의 기본 문으로 들어간다(포트는 다음 장)

daehyub71.github.io — 찾아갈 컴퓨터의 이름(호스트 이름) / GitHub가 계정 이름으로 내준 하위 도메인

/seoul-trade-insight/ — 경로 / 저장소 이름이 그대로 붙었다

경로는 도메인의 일부가 아닙니다

GitHub Pages는 저장소로 만든 사이트를 계정 이름 주소 밑에, 저장소 이름을 경로로 붙여 열어 줍니다. 그리고 배포 설정 파일인 deploy.yml이 같은 저장소 이름을 사이트의 기본 경로(basePath)로 넣어서, 화면 안의 링크가 그 경로를 따르게 합니다. 저장소 설명서에서 말하는, 사이트 경로에 저장소 이름이 자동으로 들어간다는 내용이 바로 이 일입니다.

물음표 뒤의 쪽지 — 상세 화면 주소

web/ 폴더 안의 README에는 상권 하나를 자세히 보여 주는 화면의 주소 모양도 적혀 있습니다. 실제 값을 넣으면 이렇습니다.

https://daehyub71.github.io/seoul-trade-insight/area/?ta=3110131&biz=CS100010

ta=3110131 — 데이터 파일(area_index.json)에서 찾아보면 성수동 카페거리

biz=CS100010 — 데이터 파일(biz_index.json)에서 찾아보면 커피 음료 / 실제로 열면 성수동 카페거리의 커피 음료 점수가 나옵니다

물음표 뒤의 ta와 biz는 도메인도 경로도 아닌, 질의 문자열이라는 부분입니다. 상세 화면에 어느 상권, 어느 업종을 보여 줄지 알려 주는 쪽지이고, 화면 코드가 이 값을 읽어서 씁니다.

AI에게 조각마다 근거를 붙이게 하기

AI에게 "이 사이트 주소 설명해 줘"라고 막연하게 물으면, 어느 사이트에나 해당하는 일반적인 설명만 길게 돌아옵니다. 주소 조각마다 근거가 된 파일을 붙이게 해 보세요.

README.md, web/README.md, .github/workflows/deploy.yml 만 근거로 답해 줘.
1) 이 주소를 방식 · 호스트 이름 · 경로 · 질의 문자열로 나누고 역할을 적어 줘.
https://daehyub71.github.io/seoul-trade-insight/area/?ta=3110131&biz=CS100010
2) 조각마다 근거가 된 파일과 그 줄을 그대로 옮겨 줘. 파일에 없는 설명은 「일반 지식」으로 표시해 줘.
3) 이 사이트의 IP 주소는 적지 마. 내가 nslookup으로 직접 확인할 테니 명령만 알려 줘.

AI의 답은 초안입니다. 세 가지를 직접 맞춰 봅니다.

✓ 옮긴 줄이 파일에 정말 있는가 — 특히 기본 경로(basePath) 줄
✓ AI가 말하는 「도메인」이 github.io인가, daehyub71.github.io인가
✓ 근거도 없이 특정 IP를 정답처럼 말하지 않는가

DNS 조회 — 접속 전에 먼저 하는 일

브라우저가 도메인으로 접속하려면, 먼저 그 이름의 IP 주소를 알아내야 합니다. 이것을 DNS 조회라고 합니다. DNS는 거대한 전화번호부 한 권을 한곳에 둔 방식이 아니라, 이름의 오른쪽 끝부터 구역마다 담당이 나뉜 시스템입니다. 움직이는 그림으로 길을 따라가 봅니다.

① 가까운 기억부터 찾아봅니다. 브라우저와 운영체제가 최근 답을 잠시 적어 둔 캐시, 그리고 hosts라는 작은 파일입니다.
② 없으면 네트워크 설정에 정해 둔 리졸버, 곧 주소를 대신 찾아 주는 서버에게 묻습니다.
③ 리졸버도 모르면 맨 위의 루트 서버에게 묻습니다. 루트는 ".com 담당은 저쪽"이라며 다음 창구만 알려 줍니다.
④ .com 담당 서버는 example.com을 책임지는 네임 서버를 알려 줍니다.
⑤ 담당 서버가 마침내 주소를 알려 주고, "이 답은 300초 동안 기억해도 된다"고 덧붙입니다.
⑥ 답은 돌아오는 길목의 캐시에 남고, 브라우저는 이 주소로 접속을 시작합니다. 같은 이름을 다시 물으면 대부분 가까운 기억에서 바로 끝납니다.

묻고 다니는 일은 브라우저가 아니라 리졸버가 대신 합니다. 단계보다 이것만 기억하세요. DNS는 웹페이지를 내려 주는 서버가 아니라, 접속에 필요한 주소를 찾아 주는 과정입니다.

간판 · 안내 · 가게 — 서로를 대신하지 못한다

손님이 지도를 보고 가게를 찾아왔고, 문 위에는 반짝이는 새 간판도 있습니다. 그런데 유리창 너머 가게 안이 텅 비어 있습니다. 물건을 실은 트럭은 아직 오는 중입니다. 도메인을 등록했다고 웹사이트가 저절로 생기지는 않습니다. 셋은 함께 쓰이지만 서로를 대신하지 못합니다.

도메인 = 간판 / 상권 사이트에서는 daehyub71.github.io — GitHub가 내줌

DNS = 간판을 건물 주소에 이어 주는 안내 / GitHub가 관리

웹 서버 = 실제로 손님을 맞는 가게 / GitHub Pages — deploy.yml이 채움

가게 안을 채우는 deploy.yml은 main 브랜치에 코드가 올라올 때마다 web/ 폴더를 빌드해서, 미리 만들어 둔 화면 파일을 GitHub Pages에 올립니다. 이 단계가 처음부터 실패했다면 간판만 있는 빈 가게가 됩니다.

나중에 직접 산 도메인을 연결할 때 AI가 안내하는 A 레코드는 「이 이름의 주소는 이 IP」라고 적는 설정 한 줄이고, CNAME 레코드는 「이 이름은 저 이름의 별칭」이라고 적는 설정 한 줄입니다. 어느 쪽을 쓸지는 배포 서비스의 안내를 따릅니다.

TTL — 「DNS가 반영되려면 시간이 걸린다」의 정체

가게가 길 건너로 이사했습니다. 휴대전화에 남은 옛 정보를 본 사람은 셔터가 내려진 옛 자리로 오고, 방금 새로 찾아본 사람은 새 자리로 갑니다. 언제 찾아봤느냐에 따라 가는 곳이 달라집니다.

DNS의 답에는 TTL이라는 숫자가 붙어 옵니다. 이 답을 몇 초 동안 기억해도 되는지 알려 주는 숫자이고, 도메인을 관리하는 쪽이 정해 둡니다.

www.example.com → 192.0.2.10  TTL 300  (300초 동안 기억해도 된다는 뜻 · 예시)

움직이는 그림에서는 사람 셋이 서로 다른 때에 옛 주소를 기억해 두었습니다. 운영자가 주소를 바꿔도 모두 한동안 옛 서버로 가고, TTL이 먼저 끝난 사람부터 다시 물어 새 주소를 받습니다. 그 사이에는 같은 이름인데도 사람마다 다른 서버를 봅니다.

새 주소가 저절로 퍼져 나가는 게 아니라, 기억해 둔 시간이 끝나서 다시 묻는 것입니다. 「DNS가 반영되기를 기다린다」는 말은 이 기억들이 하나씩 끝나기를 기다린다는 뜻입니다. 그래서 주소를 바꿀 계획이 있으면 미리 TTL을 짧게 줄여 두는 것이 흔히 하는 준비입니다.

그러니 앱을 옮긴 뒤 새 화면과 예전 화면이 섞여 보여도, 코드가 두 벌로 갈라졌다고 바로 판단하지 마세요. 헷갈리기 쉬운 캐시가 둘 있습니다.

DNS 캐시 — 이름을 주소로 바꾼 결과를 기억한다

브라우저의 페이지 캐시 — 이미 내려받은 화면 파일(HTML · 이미지 · 스크립트)을 기억한다 → 어느 쪽 기억 때문인지부터 나눠 봅니다

공인 IP와 사설 IP — 둘 다 맞는 숫자

집 와이파이에 연결된 노트북에서 IP를 확인하면 192.168로 시작하는 숫자가 나오는데, 외부 사이트에서 내 IP를 확인하면 전혀 다른 숫자가 보입니다. 둘 다 맞습니다.

집 안에서 본 내 IP — 192.168.0.23 / 사설 IP, 네트워크 안에서만 쓰인다

바깥 사이트가 본 내 IP — 203.0.113.5(예) / 공인 IP, 공개 인터넷에서 보인다

사설 IP로 쓰라고 정해 둔 범위는 10., 172.16~172.31, 192.168로 시작하는 세 덩어리입니다. 바깥 인터넷은 이 번호로 길을 찾지 않아서, 집집마다 같은 번호를 써도 문제가 없습니다.

아파트 단지로 빗대 봅니다. 동과 호수만 적힌 쪽지로는 비슷한 단지가 여럿이라 배달 기사가 찾아올 수 없습니다. 단지 밖에서 찾아오려면 도로명 주소가 필요하고, 이 도로명 주소가 공인 IP, 동과 호수가 사설 IP에 해당합니다. 단지 안으로 들어오면 경비실이 동과 호수를 보고 집까지 전해 주는데, 네트워크에서는 공유기가 이 경비실 역할을 합니다.

NAT — 공유기가 「보내는 사람」 칸을 바꿔 적는다

집 안 노트북은 어떻게 바깥 사이트와 이야기할까요? 공유기가 보내는 사람 칸을 자기 바깥 주소로 바꿔 적고, 돌아온 답은 기록표를 보고 원래 기기에 돌려줍니다. 이것을 NAT이라고 합니다.

노트북(192.168.0.23)이 보낸 봉투는 공유기에서 보내는 사람 칸이 203.0.113.5(예)로 바뀌고, 웹사이트에는 이 바깥 주소만 보입니다. 태블릿이 보내도 바깥에서는 같은 주소이고, 둘을 구분하는 것은 공유기의 기록표뿐입니다. 반대로 바깥에서 사설 주소로 곧장 찾아오려는 봉투는 길을 찾지 못합니다.

그래서 조심할 것이 두 가지 있습니다. 첫째, 외부에서 보이는 IP를 내 노트북만의 고정 주소라고 단정하면 안 됩니다. 여러 집이 함께 쓰기도 하고, 주소가 바뀌기도 합니다.

둘째, 집 안 사설 주소를 안다고 해서 친구가 인터넷에서 그 주소로 내 노트북에 들어올 수는 없습니다. 이 차이는 다음 장에서 localhost와 포트를 배울 때 다시 중요해집니다.

URL — 도메인보다 더 긴 주소

주소창의 문자열 전체를 URL이라고 부릅니다. 도메인은 URL의 한 조각일 뿐입니다. 가게에 빗대면 도메인은 가게 이름이고, URL은 어느 문으로 들어가 어느 진열대에서 무엇을 달라고 할지까지 적은 안내문입니다.

https://shop.example.com:443/items?id=7#review

https — 통신 방식(어떤 규칙으로 통신할지)

shop.example.com — 호스트 이름(찾아갈 컴퓨터, 오른쪽부터 읽는다)

:443 — 포트(출입문 번호, https의 기본 문이라 보통 생략)

/items — 경로(서버 안의 어떤 자료인지)

?id=7 — 질의 문자열(덧붙이는 조건, 여러 개면 & 기호로 잇는다)

#review — 조각(서버로 보내지 않고 브라우저가 페이지 안 위치를 찾는 데 쓴다)

상권 사이트의 상세 화면 주소도 같은 틀에 들어갑니다. /seoul-trade-insight/area/가 경로이고, ta=3110131&biz=CS100010이 질의 문자열입니다.

URL의 경로는 파일 경로(2장)와 닮았지만 서버의 폴더와 꼭 같지는 않습니다. /seoul-trade-insight/도 그런 폴더가 있어서가 아니라 GitHub Pages와 배포 설정이 만든 경로입니다.

그리고 사이트 이름을 대충 훑어보기만 하면 속을 때가 있습니다.

https://example.com.fake-site.invalid/login

진짜 등록된 도메인은 오른쪽 끝의 fake-site.invalid이고, 앞의 example.com은 하위 이름일 뿐입니다. 익숙한 이름이 앞에 보여도, 진짜 주인은 늘 오른쪽 끝에서 확인하세요.

하나의 도메인, 여러 서버

대형 공연장에 손님이 몰리면, 간판은 하나여도 로비의 안내 직원이 줄을 여러 창구로 나눠 보냅니다. 웹 서비스도 이름 하나 뒤에 여러 서버와 여러 IP 주소가 놓일 수 있습니다. 여기서 간판은 도메인을, 창구는 서버를 빗댄 것입니다. 실제로 요청을 나누는 일은 로드 밸런서라는 장치가 따로 맡는 경우가 많습니다.

도메인 이름은 이용자에게 늘 같은 출입구를 보여 주고, 그 뒤의 실제 컴퓨터 구성은 바뀔 수 있다는 것. 이 원리 하나만 기억하면 됩니다. 오늘 예제 사이트 이름도 직접 물어보면 주소가 여러 줄로 돌아옵니다.

PS C:\Users\사용자이름> nslookup daehyub71.github.io
…
Addresses:  192.0.2.153
            192.0.2.154
            192.0.2.155
(출력은 예시)

내 화면에선 열리는데 친구는 못 연다

AI가 배포가 완료됐다며 보내 준 주소가 내 노트북에서는 잘 열리는데, 친구 휴대전화에서는 「사이트에 연결할 수 없음」이 뜹니다.

이럴 때는 원인을 순서대로 나눠 봅니다.

① 공개된 주소가 맞는가
② 이름이 IP로 바뀌는가
③ 그 서버가 응답하는가
④ 보안 경고나 네트워크 정책 때문은 아닌가

가장 먼저 볼 것은 첫 번째입니다. AI가 보낸 주소가 localhost나 127.0.0.1, 192.168로 시작하는 내 컴퓨터나 우리 집 안의 주소라면, 친구 쪽에서는 처음부터 열릴 수 없습니다.

AI에게는 이렇게 부탁합니다.

원인을 하나로 정하지 말고, 어느 단계에서 끊겼는지 같이 확인하자.
1) 공개 주소인가 2) 이름이 IP로 풀리나(nslookup) 3) 서버가 응답하나(브라우저 · curl) 4) 친구 쪽 경고 · 정책
단계마다 내가 직접 확인할 방법을 알려 주고, 원인을 찾기 전에는 DNS 설정을 바꾸지 마.

DNS 설정 변경은 같은 도메인을 쓰는 다른 서비스에도 영향을 주니, 회사 도메인은 관리자 승인 없이 바꾸지 않습니다.

직접 확인하기 — DNS에 물어보고, 내 사설 IP 보기

설정은 바꾸지 않고 확인만 합니다. 윈도우는 시작 단추에서 「PowerShell」을, 맥은 Command와 스페이스로 「터미널」을 검색해 엽니다. 아래 출력은 형식만 살린 예시이고, 실제 숫자는 사람마다, 때마다 다릅니다.

① DNS에 물어보기 — nslookup은 윈도우와 맥에서 똑같이 씁니다.

윈도우 · PowerShell (출력은 예시)
PS C:\Users\사용자이름> nslookup example.com
서버:    UnKnown
Address:  192.0.2.53
권한 없는 응답:
이름:    example.com
Addresses:  198.51.100.24
            203.0.113.17

서버 줄은 내가 물어본 리졸버이고, 권한 없는 응답은 담당 서버가 아니라 리졸버가 전해 준 답이라는 표시입니다. 맥에서는 Server, Non-authoritative answer로 나오고 주소를 Address 줄마다 하나씩 보여 줍니다.

같은 명령으로 nslookup daehyub71.github.io도 물어보고, 주소가 몇 줄 나오는지 세어 보세요.

② TTL 보기 — 윈도우는 PowerShell에서 Resolve-DnsName example.com -Type A를 입력하면 TTL 칸을 함께 보여 줍니다. 맥은 dig라는 명령이 답을 더 자세히 보여 줍니다.

맥 · 터미널 (출력은 예시)
$ dig example.com +noall +answer
example.com.  223  IN  A  198.51.100.24

두 번째 칸의 223이 캐시에 남은 시간(TTL, 초)이고, 잠시 뒤 다시 실행하면 줄어 있습니다.

③ 내 사설 IP 확인하기

윈도우 · PowerShell (출력은 예시)
PS C:\Users\사용자이름> ipconfig
…
   IPv4 주소 . . . . . . . . . : 192.168.0.23

맥 · 터미널 (출력은 예시)
$ ipconfig getifaddr en0
192.168.0.23
(또는 시스템 설정 → 네트워크 → Wi-Fi → 세부사항)

나온 숫자가 사설 범위 세 덩어리 가운데 어디에 속하는지 보세요. 네트워크 설정은 건드리지 말고, 내 IP 확인 사이트에 나오는 공인 주소는 다른 사람에게 알려 주지 마세요.

흔한 오해 다섯 가지

IP 주소는 평생 붙어 있는 번호다? — 연결한 네트워크에 따라 바뀌고, 여러 개일 수도 있습니다.

도메인 하나는 IP 하나다? — 도메인 하나가 여러 주소를 가리키기도 하고, 여러 사이트가 한 주소를 함께 쓰기도 합니다.

DNS가 웹페이지를 만들어 준다? — DNS는 이름을 주소로 바꿔 줄 뿐이고, 페이지는 웹 서버가 내줍니다.

도메인을 샀으니 앱이 공개됐다? — 도메인을 사도 배포, 연결, 보안 설정이 아직 남아 있을 수 있습니다.

www는 필수다? — 흔히 쓰는 이름 가운데 하나일 뿐입니다.

한 장 요약

IP 주소는 통신할 대상을 찾는 네트워크 주소이고, 평생 고정된 번호가 아닙니다(IPv4 · IPv6 두 형식). 도메인은 사람이 기억하는 간판이고, 오른쪽으로 갈수록 큰 단위입니다. DNS는 구역별 안내소를 거쳐 이름을 주소로 바꾸고, 그 답은 TTL 동안 캐시에 남습니다. 사설 IP는 집 안에서만 통하는 번호이고, 공유기가 NAT으로 공인 IP와 이어 줍니다. URL은 방식, 호스트, 포트, 경로, 질의, 조각을 담은 전체 안내문이고, 도메인은 그중 한 조각입니다.

확인 문제 다섯 개(도메인 등록과 웹앱 배포는 왜 별개의 일일까? 등)와 풀이는 강의 자료와 움직이는 개념 노트에 있습니다.

다음 글에서는 Part1-5 localhost와 포트를 다룹니다. 이름을 주소로 바꿔 건물을 찾았다면, 이제 그 건물의 어느 문을 두드려야 할까요? AI가 「localhost:8000으로 접속하세요」라고 할 때의 그 주소, localhost와 포트를 만납니다.
